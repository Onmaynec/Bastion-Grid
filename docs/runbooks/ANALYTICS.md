# Поиск и проверка правил v0.5.0

## Поиск

В «События» откройте «Фильтры». Доступны event_type, source_id, asset_id (UUID), outcome и диапазон времени события. Пустые поля не применяются. Все заданные фильтры объединяются через AND. Время задаётся ISO 8601 с часовым поясом: `2026-11-14T10:00:00+03:00` эквивалентно `2026-11-14T07:00:00Z`.

Диапазон полуоткрытый: time_from включается, time_to не включается. Начало должно быть раньше конца. «Сбросить» очищает фильтры; «Ещё события» загружает следующую страницу без изменения фильтров. API `POST /api/v1/events/search` принимает limit 1–100 (по умолчанию 50) и after — последовательность последнего события. Порядок остаётся ingest_sequence, а не event_time.

Scope активов и тенант проверяются до выдачи страницы. Пустая выборка для чужого asset_id не раскрывает его существование. Страницы не закреплены за одним snapshot: новые события могут появляться между запросами, а смена политики меняет видимость. Внутри неизменного набора курсор не повторяет события. Индексы аналитического хранилища, watermark, распределённый поиск и R1 benchmark не реализованы.

## Правила

Старый формат field/operator/value продолжает работать. Новый формат:

```json
{
  "name": "Неуспешная аутентификация с высоким уровнем",
  "severity": "high",
  "match": "all",
  "conditions": [
    {"field": "outcome", "operator": "eq", "value": "failure"},
    {"field": "severity", "operator": "gte", "value": 4}
  ]
}
```

API допускает 1–8 условий. all означает AND, any — OR, по умолчанию all. В UI можно задать одно или два условия; для 3–8 используйте API. Поля: event_type, outcome, process_name, severity. Операторы: eq, gte, contains. Eq сравнивает тип и значение; gte принимает числовое значение, contains — непустую строку. Boolean не является числом. Не смешивайте conditions с field/operator/value верхнего уровня. Вложенные выражения, регулярные выражения и временная корреляция отсутствуют.

Созданное правило остаётся черновиком. Публикация требует другого согласующего и If-Match; опубликованные правила не редактируются. В объяснении алерта составного правила указаны условия, режим и результат каждого условия. Старый формат объяснения одиночных правил сохранён.

## Примеры до публикации

Нажмите «Проверить» у правила либо вызовите `POST /api/v1/rules/{id}/test`:

```json
{
  "fixtures": [
    {"attributes": {"outcome": "failure", "severity": 4}, "expected": true},
    {"attributes": {"outcome": "success", "severity": 4}, "expected": false}
  ]
}
```

Допускаются 1–100 примеров, до 32 атрибутов в каждом и до 64 KiB канонического JSON тела. Результат содержит номер примера, matched, expected, passed и результаты условий. Несовпадение ожидания — обычный результат проверки с HTTP 200, не ошибка API. Fixtures и результаты не сохраняются; алерты, события и аудит не изменяются. Это ручная проверка, а не обязательный gate публикации.

Проверка примеров, replay и живая детекция используют один вычислитель. Replay читает правило и до 10 000 событий из согласованного SQLite snapshot, возвращает совпавшие sequence и не создаёт алертов. При превышении бюджета — 422. Ни replay, ни fixtures не являются фоновыми jobs. Правила и эти операции недоступны scoped identities, поскольку глобальное правило может раскрывать события за их scope.

## Обновление

Схема сервера остаётся 3. Остановите старый сервер и запустите v0.5.0 без init. Старые правила сохраняют смысл; новые составные правила не поддерживаются версиями до 0.5.0. Для отката используйте резервную копию, сделанную до создания составных правил, и старую версию приложения. Не запускайте старый worker на БД с новыми правилами.
