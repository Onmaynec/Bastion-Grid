# Управление доступом и обновление 0.2.0

## Обновление 0.1.0

1. Остановите все процессы старой версии, работающие с БД.
2. Сохраните архив исходной версии и резервную копию БД. SQLite backup API предпочтительнее копирования живого WAL-файла.
3. Замените исходники и выполните `python -m bastion serve --lab` с прежним `--db`, если он использовался.
4. Перед изменением существующей схемы 1 создаётся snapshot `<database>.pre-v2-<random>.sqlite3`. Если backup не удалось создать, обновление прерывается.
5. Миграция добавляет stable identity ID, policy/revision и metadata сеансов. Браузерные сеансы закрываются. Неистёкшие ключи, события, кейсы и evidence сохраняются.
6. Снова войдите прежним ключом. `init` повторять не нужно.

Не запускайте старый бинарный код на обновлённой БД. Для отката остановите приложение, восстановите исходники 0.1.0 и запустите их на pre-v2 snapshot. Новые записи после обновления в этом snapshot отсутствуют; перед rollback сохраните текущую БД отдельно. Миграции только вперёд. Будущая неизвестная схема блокирует старт.

## Учётные записи

Раздел «Доступ» доступен admin с полным scope. Новый субъект уникален внутри tenant. Выберите роль, TTL 60–86400 секунд, группы и максимальную чувствительность. Новый ключ отображается один раз; окно очищается при закрытии, в списках/аудите/БД plaintext не сохраняется.

Группы сравниваются точно, с учётом регистра. `*` означает все группы и не комбинируется с другими значениями. Уровни возрастают: public → internal → confidential → restricted. Активы версии 0.1.0 без поля sensitivity трактуются как internal. Группа legacy-актива по умолчанию — lab.

«Только назначенные себе кейсы» ограничивает кейсы, связанные доказательства и заявки по owner==subject. Эта настройка не скрывает разрешённые по группе события и алерты: аналитик может исследовать их и открыть собственный кейс. Связи case→alert→asset и evidence/response→case проверяются на сервере.

Ограниченный admin не может управлять identities, читать полный audit/export и глобальные правила. Это предотвращает обход scope через повышение прав, replay или экспорт. Обычные чтения скрывают недоступные ресурсы; get/update чужого или недоступного ресурса возвращает 404.

## Ротация и отзыв

«Новый ключ» атомарно инвалидирует старый bearer и все cookie-сеансы, повышает версию и показывает новый ключ. Ротация также восстанавливает отозванную/истёкшую запись; роль и scope не расширяются. При ротации собственной записи сохраните новый ключ до закрытия окна, затем войдите заново.

«Отозвать» требует причину и If-Match. Отзыв последнего активного unrestricted admin через API запрещён — сначала создайте второго администратора. Смена policy тоже закрывает сеансы и защищена If-Match. Уже начавшаяся операция записи повторно проверяет identity version и существование сеанса под write lock.

## Сеансы

Раздел «Сеансы» показывает subject, роль, время создания, последнего обращения и истечения. Пользователь видит и завершает собственные сеансы; полный admin — сеансы tenant. Cookie, CSRF и хеши ключей не возвращаются в списке. Завершение одного сеанса не отзывает другие.

## Все ключи истекли

В 0.2.0 нет recovery-входа без действующего admin key. Не редактируйте БД вручную и не публикуйте токены. Сохраняйте второй действующий лабораторный admin и ротируйте до истечения. Для нового эксперимента используйте отдельную БД; это не продление доступа к старой. Безопасный break-glass остаётся отдельным требованием IAM-008.
