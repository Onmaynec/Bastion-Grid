# Заявки и доказательства v0.6.0

## Состояния заявок

Заявка создаётся как PENDING_APPROVAL с TTL 30–900 секунд. Два независимых согласующих переводят её в APPROVED. Действия на устройствах по-прежнему не исполняются: simulation_only=true, execution_enabled=false.

| Операция | Кто может выполнить | Допустимое состояние | Результат |
|---|---|---|---|
| Согласовать | admin/lead, кроме инициатора; один голос на субъект | PENDING_APPROVAL | Голос; после второго APPROVED |
| Отказать | admin/lead, кроме инициатора | PENDING_APPROVAL | REJECTED |
| Отменить | Инициатор или admin/lead | PENDING_APPROVAL, APPROVED | CANCELLED |
| Истечение TTL | Фоновый worker | PENDING_APPROVAL, APPROVED | EXPIRED |

Все ручные операции проверяют tenant, scope связанных объектов, действующий доступ и If-Match. Для отказа/отмены обязательна причина длиной 1–2000 символов. Они доступны в разделе «Реагирование», а через API — POST /api/v1/responses/{id}/reject и /cancel. Отказ не требует двух голосов: он прекращает согласование. После отказа, отмены или истечения заявку нельзя вернуть в работу; создайте новую при необходимости.

Карточка содержит resolution.actor/reason/time. Голоса сохраняются для истории. Одновременное согласование и отмена с одной версией не могут оба завершиться успешно: проигравший запрос получает 409. Повышенная роль не снимает scope.

Worker обрабатывает до 100 истёкших заявок за цикл перед детекцией. Изменение статуса, увеличение версии и аудит response.expired выполняются атомарно; повторные циклы не добавляют повторный аудит. Пока сервер выключен, переход не выполняется; после старта просроченные заявки обрабатываются порциями. API согласования, отказа и отмены отклоняет истёкшую заявку независимо от задержки worker. UI показывает истечение для pending/approved, но не подменяет ранее сохранённые REJECTED/CANCELLED.

## Проверка экспорта

Экспорт evidence bundle сохраняет формат bastion-evidence-v1. Проверяйте его локально:

```bash
python -m bastion verify bundle.json
python -m bastion verify bundle.json --checkpoint <64-символьный-SHA256>
```

Успех возвращает JSON valid=true и код 0. Ошибка формата/целостности возвращает valid=false, error_code и код 1, без содержимого доказательств и traceback. Отсутствующий или невалидный JSON-файл также даёт контролируемую ошибку. Если --checkpoint передан, он обязан быть 64-символьным SHA-256 в нижнем регистре; пустая строка больше не отключает проверку.

Verifier проверяет типы полей, возрастающие положительные seq аудита, цепочку хешей, checkpoint, уникальность и комплектность evidence IDs, Base64, размер, SHA-256 и связь объекта с единственной записью evidence.acquired. Связи получения индексируются за один проход по аудиту; вложенный проход по всей истории для каждого доказательства удалён. JSON целиком читается в память — потоковая обработка больших архивов не реализована.

Seq глобален для БД, поэтому в экспорте одного тенанта допустимы пропуски. Проверка seq проверяет порядок, а не криптографически удостоверяет номера. Формат не подписан: signature должен быть null, trust — unanchored-local-hash-chain. Verifier не принимает произвольную строку signature как доказательство подписи.

Доверенный checkpoint нужно получить отдельным доверенным каналом. Без него проверка подтверждает внутреннюю согласованность, но не защищает от администратора БД, который перепишет всю историю и пересчитает хеши. PKI/KMS, цифровые подписи, WORM и защищённое время отсутствуют. Это не юридическая аттестация доказательств.

## Обновление

Схема БД остаётся 3. Остановите старый сервер и запустите новую версию без init. Старые экспорты, созданные приложением, сохраняют совместимость. Повреждённые и неоднозначные структуры теперь отклоняются строже. При старте новые worker сохранят EXPIRED для старых просроченных pending/approved заявок. Для отката сохраните backup до обновления: старые версии не поддерживают весь жизненный цикл CANCELLED/REJECTED/EXPIRED.
