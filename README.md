# BASTION GRID

Платформа для защитной телеметрии, расследований и управляемого реагирования.

**Текущая версия: 0.6.0 — доказательства и жизненный цикл заявок в локальном стенде.** Реализован сквозной путь от синтетического события до кейса, доказательства и согласованной заявки. Полное ТЗ OMEGA R2 ещё не выполнено; промышленное внедрение этой версии не предусмотрено.

## Запуск

Нужен Python 3.12 или новее. У приложения нет сторонних Python-зависимостей, CDN, внешних API и обязательного доступа в интернет.

```bash
python -m bastion init
python -m bastion serve --lab
```

Откройте <http://127.0.0.1:8080>. Команда `init` выводит путь к локальному JSON-файлу с ключами. Для входа используйте поле `token` учётной записи `operator`. Ключи действуют 24 часа, браузерный сеанс — максимум 15 минут. Файл ключей и БД находятся в `var/` и не входят в Git.

На Windows при необходимости замените `python` на `py -3.12`. Команды выполняются из корня репозитория. Сервис намеренно слушает только loopback. Не публикуйте его через reverse proxy: лабораторный профиль не поддерживает production identity, TLS и распределённую эксплуатацию.

В отдельном терминале заполните стенд через HTTP API:

```bash
python tools/demo.py
```

Сценарий создаёт 4 актива, 1 правило, 12 событий, повторно отправляет те же события, проверяет 4 алерта, создаёт кейс и доказательство, получает два независимых согласования. Повторный запуск создаёт новую серию объектов. Данные явно синтетические.

## Что работает

- Серверная привязка тенанта, пять ролей, ограниченный collector, немедленная проверка отзыва при каждом запросе.
- HttpOnly/SameSite cookie, CSRF-защита, Host/Origin проверки, CSP, ограничение попыток входа.
- Каталог активов с UUID, ОС, владельцем, критичностью и последним наблюдением.
- Атомарный batch до 100 событий; SHA-256 fingerprint; устойчивый ACK после SQLite commit; конфликт при повторном ID с другим содержимым.
- Очередь обработки в БД, возобновление после повторного открытия, транзакционная дедупликация алертов.
- Типизированные операторы `eq`, `gte`, `contains`; независимая публикация; replay без изменения алертов; объяснение срабатывания.
- Идемпотентное создание кейсов, автомат состояний, `If-Match`, история переходов, текстовые доказательства.
- Allowlist заявок, оценка одного актива, TTL 30–900 секунд, два согласующих помимо инициатора.
- Экспорт доказательств с цепочкой хешей, независимая проверка, согласованный backup SQLite.
- Русская консоль: обзор, оповещения, активы, события, правила, расследования, реагирование, аудит, доступ, сеансы и телеметрия.

**Заявки не исполняются на устройствах.** `APPROVED` означает только завершение согласования. В каждой заявке указаны `simulation_only: true` и `execution_enabled: false`. Сетевой изоляции, удалённого терминала и системных endpoint-служб в этой версии нет.

## Новое в 0.6.0

Добавлены отказ в согласовании, отмена заявки и фоновое сохранение EXPIRED. Причина, автор и время завершения доступны в карточке; прежние голоса сохраняются. Проверка evidence bundle стала строже, ошибки CLI возвращают структурированный результат без traceback. [Инструкция и ограничения](docs/runbooks/RESPONSE_EVIDENCE.md).

Исполнение на устройствах остаётся отключённым. Перед обновлением остановите сервер и сохраните backup; схема остаётся 3, повторный init не нужен. Collector и поиск из предыдущих версий продолжают работать.

## Проверки

```bash
python -m unittest discover -s tests -v
python -m compileall -q bastion tools tests
python tools/build_contract.py
python tools/build_traceability.py
python -m bastion verify var/demo-evidence.json
```

146 автоматизированных тестов покрывают ядро, HTTP, контракт и полноту матрицы требований. Это локальные регрессии, а не прохождение 192 формальных приёмочных испытаний RFP.

Опциональный браузерный сценарий требует отдельно установленного Playwright/Chromium и заполненного стенда:

```bash
python -m pip install playwright
python -m playwright install chromium
python -m tools.ui_smoke
```

На Ubuntu 24.04 в GitHub Actions запускается браузерная проверка. Базовый сценарий 0.1.0 проверял 8 разделов. Для 0.2.0 добавлены разделы доступа и сеансов, создание ограниченной записи, ротация и отзыв ключа. В 0.3.0 сценарий проверяет также источник, паузу/возобновление, квоты и повтор из очереди ошибок. Точный результат текущего коммита смотрите в GitHub Actions. Скриншоты сохраняются в артефакте `soc-ui-check`. Локальная ограниченная среда может запрещать запуск Chromium; CI использует отдельный runner.

## Роли стенда

| Учётная запись | Назначение |
|---|---|
| operator | Активы, черновики правил, чтение, кейсы и заявки |
| analyst | Чтение, расследования, доказательства, заявки |
| reviewer-one, reviewer-two | Независимая публикация и согласование |
| auditor | Чтение и экспорт аудита |
| collector | Только приём событий, вход в UI запрещён |

Повышенная роль не разрешает согласовать собственную заявку. Доступ дополнительно ограничивается группами активов, уровнем чувствительности и назначением кейсов. OIDC и MFA ещё отсутствуют: лабораторные ключи не заменяют целевую IAM-модель.

## Ограничения

SQLite, стандартный HTTP server и Python выбраны только для воспроизводимого локального контура. Production PostgreSQL, OIDC/PKCE/MFA, mTLS, KMS, подписанные агенты, шина событий, аналитическое хранилище, NDR/cloud/OT, HA/DR и масштаб OMEGA не реализованы. Поиск упорядочен по последовательности приёма, не по целевому `(timestamp, event_id)`. Списки объектов ограничены первыми 500 элементами; аудит экспортируется целиком. Квоты ограничивают локальный приём и backlog; retention, общий предел размера БД и промышленное распределение нагрузки отсутствуют.

Цепочка SHA-256 не защищает от администратора БД, который пересчитает всю историю. Проверяющий должен получить доверенный checkpoint независимым каналом. Цифровые подписи и доверенное время не реализованы. Внешняя сертификация, производительность R1/R2 и готовность к эксплуатации не заявляются.
